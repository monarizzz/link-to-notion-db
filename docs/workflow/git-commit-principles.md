# コミット分割の原則

コミットの分け方と並べる順序の判断基準。
粒度とメッセージの必須ルールは [AGENTS.md の「コミット」節](../../AGENTS.md#コミット) にある。
ここでは、その前提となる考え方と AGENTS.md に書き切れない判断基準を扱う。

## 粒度

### 1 コミット = 1 つの論理的変更

- 論理的変更とは、レビュアーが 1 つのまとまりとして理解できる単位
- 複数ファイルにまたがってもよい。逆に 1 ファイル内でも関心事が違えば分ける
- 判断基準: 「このコミットを revert したとき何が失われるか」を一文で言えるか

### 型チェックが通る単位で切る

- 各コミットの時点で `npx tsc --noEmit` が通ること
- 理由: `git bisect` で壊れたコミットを特定できるようにするため
- やむを得ず途中のコミットが壊れる場合は、そのことを本文に書く

### 小さすぎても分けない

- typo 修正 1 件だけを独立コミットにするのは分けすぎ
- 関連する小さな修正はまとめる。目安は diff 全体を 30 秒で把握できること

## 分類

### 生成物と手書きを分ける

- shadcn CLI が生成したコンポーネント（`src/libs/shadcn/`）は、手書きのコードと別のコミットにする
- 例外: `package-lock.json` は `package.json` と同じコミットにする。食い違うと `npm ci` が止まる

### デザインファイルとコードを分ける

- `.pen` ファイルの変更は実装のコミットに混ぜない。差分をレビューで読めないため

### リファクタと機能追加を混ぜない

- 機能追加の前にリファクタが必要なら、先にリファクタのコミットを作る
- 見た目と振る舞いが変わらないものをリファクタとする。Storybook の表示やテスト結果が変わるならリファクタではない

### テストと実装

- 既定はテストと実装を 1 コミットにする。`.stories.tsx` もコンポーネントと同じコミットに置く
- バグ修正は「再現するテストを追加する」→「修正する」の 2 コミットにしてもよい。その場合は、1 つ目のコミットでテストが落ちることを本文に書く

## 順序

### 依存の下から上へ

1. ツール・設定（`package.json`、ESLint 設定、`.github/workflows/`）
2. 汎用ライブラリ・設定（`src/libs/`）
3. 外部サービス連携（`src/infra/`）
4. 共通コンポーネント（`src/commons/`）
5. 機能コンポーネント（`src/features/`）
6. ルーティングの結線（`src/app/`）
7. ドキュメント（`AGENTS.md`、`README.md`、`docs/`）

各コミットが、それより前のコミットだけに依存するように並べる。
上の層を先にコミットすると、そのコミット単独では import 先が無く型が付かない。

### バグ修正は先に切り出す

- 機能追加の途中でバグを見つけたら、先に修正コミットを作る。別 PR に出しやすくなる

## アンチパターン

- ❌ `git add -A && git commit -m "fix"` — 何が入ったか分からない
- ❌ 「WIP」「一旦ここまで」コミット — PR を出す前に整理する
- ❌ リファクタ・バグ修正・機能追加が入った巨大コミット — 後から分けられない
- ❌ `src/app/` の結線を、結線先のコンポーネントより前にコミットする
